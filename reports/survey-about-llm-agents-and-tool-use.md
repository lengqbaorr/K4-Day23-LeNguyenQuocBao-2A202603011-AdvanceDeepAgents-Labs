# LLM Agents and Tool Use: From Prompted Reasoning to Evaluated Action

## TL;DR
- An LLM agent is best understood as a feedback-driven system that perceives a state, reasons about a goal, acts through tools or an environment, and uses the result to revise its next step; this is a stronger claim than calling a one-shot chatbot an agent [1][2].
- The field’s central design choice is where to put control: modular routers and affordance models constrain what can be executed, while language-model prompting supplies flexible reasoning and tool selection [1][3].
- Interleaving reasoning with actions improves grounding, and memory, reflection, or search can improve repeated attempts, but these additions increase inference cost and do not reliably solve exploration or long-horizon planning [2][4][5].
- Realistic benchmarks expose a large gap between short tool-call accuracy and autonomous performance: WebArena’s best GPT-4 agent reached 14.41% end-to-end success versus 78.24% for humans, while OSWorld’s best reported model reached 12.24% versus 72.36% for humans [6][7].
- Evaluation must inspect trajectories, safety, recovery, and tool faithfulness—not only final answers—because agents can fabricate tool use and propagate an early error into a plausible response [8][9][10][11].

## Background
LLM agents extend language modeling into an action loop. Instead of producing an answer from a fixed context, an agent receives a goal, observes an environment or tool result, selects an action, and repeats until it reaches a stopping condition. The distinction matters because an external action can change the world, expose new information, or create irreversible risk. MRKL Systems provided an early modular formulation: a router sends natural-language inputs to specialized “experts,” such as calculators, currency converters, databases, or other APIs, and an expert’s output can either be final or routed onward [1]. This architecture treats tool use as compositional systems engineering rather than as a capability that must reside entirely in model weights.

WebGPT showed the value of grounding answers in an interactive information environment. Its model searched, clicked, and scrolled in a text-based browser, incorporated page extracts, and recorded titles, domains, and extracts as references; training combined browser demonstrations, reward modeling, reinforcement learning, and rejection sampling [12]. ReAct then made the loop explicit by interleaving verbal reasoning with task-specific actions and observations. Its rationale was not merely stylistic: reasoning can update a plan and handle exceptions, while actions acquire information that the model does not already possess [2]. On ALFWorld, one- or two-shot ReAct prompting outperformed imitation and reinforcement-learning methods by 34 percentage points in the reported setting [2].

The resulting conceptual stack has four recurring elements: a model and objective, memory, planning, and action execution, with feedback or “rethink” connecting them [1][8]. Tool use is therefore both a capability and an interface problem. The model must decide whether a call is needed, choose the right tool, form valid arguments, interpret the result, and remain faithful about what actually happened. The survey literature describes a progression from one-step synthetic calls toward multi-turn, multi-step, stateful evaluation [8].

## Architectures for grounding language in action
There are three broad ways to constrain action. First, a router can select among explicit modules. MRKL offers modularity and compositional multi-hop routing, and it can delegate exact operations to reliable symbolic systems [1]. Its weakness is coverage: every important capability must be exposed as a module and the router must recognize when to use it. Second, a language model can learn API selection from text. Toolformer samples candidate calls, executes them, retains calls that improve future-token prediction, and fine-tunes on those examples. With a 6.7B-parameter GPT-J-based model, it improved over the best same-size baseline by 11.7, 5.2, and 18.6 points on the SQuAD, Google-RE, and T-REx portions of LAMA; API access more than doubled performance on each of ASDiv, SVAMP, and MAWPS in the reported setting [13]. This reduces annotation requirements, but it assumes that tool inputs and outputs can be represented as text and that perplexity improvement is a useful proxy for task utility.

Third, grounding can combine semantic suitability with environmental executability. SayCan scores how useful a robot skill is for the instruction (“Say”) and how likely it is to succeed in the current state (“Can”), then selects a skill using both signals [3]. In 101 zero-shot real-world kitchen tasks, affordance grounding nearly doubled performance over non-grounded baselines [3]. This is safer than asking an LLM to invent executable actions, but it depends on a maintained skill library and affordance model. Across these designs, flexibility and controllability trade off: free-form model actions cover more tasks, while routers and affordances make invalid or impossible actions easier to reject [1][13][3].

## Planning, memory, and search
ReAct uses a linear trajectory: think, act, observe, and continue. This gives a readable trace and helps diagnose whether a failure came from an incorrect belief or a bad action [2]. It is economical compared with branching search, but a mistaken early choice can constrain all subsequent steps. LATS addresses that limitation by applying Monte Carlo Tree Search over reasoning and acting steps. The language model serves as agent, value function, and optimizer; environmental feedback, backtracking, and stored verbal reflections guide exploration [5]. With GPT-3.5, LATS reported a 75.9 average WebShop score and 38.0% success, versus 53.8 and 28.0% for ReAct in the same table; with GPT-4, it reported 92.7% pass@1 on HumanEval [5]. The cost is additional model calls and the possibility that a flawed value judgment searches the wrong branches.

Memory approaches differ in what they retain. Reflexion stores a natural-language account of feedback in an episodic buffer without updating weights. It reported 91% pass@1 on HumanEval, compared with 80% for the prior GPT-4 state of the art cited in its paper [4]. Yet on a 100-environment WebShop experiment after four trials, it did not significantly beat ReAct; the authors attributed this to generic reflections and insufficient exploration for tasks requiring diverse behavior [4]. Generative Agents combine a memory stream with retrieval based on relevance, recency, and importance, periodic reflection, and recursive plan decomposition. In a 25-agent sandbox, the agents coordinated a Valentine’s Day party; the full architecture scored TrueSkill 29.89 in an interview-based believability evaluation, versus 21.21 after removing memory, planning, and reflection [4]. These results suggest that memory can improve continuity and social coherence, but not necessarily factual reliability or tool competence.

## What realistic benchmarks reveal
Benchmark design increasingly tests completed work rather than isolated action syntax. AgentBench used eight environments, 1,014 test samples, and problems estimated to require 5–50 interaction rounds; GPT-4 was best on six of eight datasets, while its House Holding success rate was 78% [8]. WebArena goes further with four functional self-hosted sites for e-commerce, forums, collaborative development, and content management. Its long-horizon tasks use functional correctness rather than exact action-sequence matching; the best GPT-4 agent reached 14.41% success against 78.24% human performance [7]. Thus a model may know the right tool call locally while failing to maintain state, navigate, or recover over a full task.

Computer-use benchmarks add visual grounding and operating-system state. OSWorld contains 369 tasks across real web and desktop applications, file I/O, and multi-application workflows on Ubuntu, Windows, and macOS. Human performance was 72.36%, compared with 12.24% for the best reported model; multi-application workflows had a highest baseline success rate of only 6.57% [6]. BrowserGym’s common API makes this expanding landscape more comparable: its ecosystem unifies six benchmarks, including WebArena, VisualWebArena, WorkArena, WebLINX, AssistantBench, and MMInA, with task counts ranging from 33 WorkArena Level-1 templates to 31,586 WebLINX templates [8].

Coding agents illustrate the value and limits of execution-based judging. SWE-bench Verified is a human-checked set of 500 repository issues evaluated by whether an agent produces a resolving patch; GPT-4o resolved 33.2% using the tested scaffold [8]. Meanwhile, tool-use evaluation is becoming multidimensional. MCP-RADAR evaluates tool utilization in the Model Context Protocol framework across five dimensions, reflecting the shift from “did the model emit a valid call?” to “did it select, invoke, and use tools appropriately?” [14].

## Reliability, safety, and evaluation
Final-answer accuracy conceals important failure modes. ToolEmu used an LM-emulated sandbox with 36 high-stakes toolkits and 144 test cases; human reviewers judged 68.8% of failures identified by the framework to be valid real-world agent failures, and the automatic evaluator found potentially severe failures in 23.9% of cases even for the safest tested agent [10]. The risks include private-data leakage, financial loss, property damage, and life-threatening outcomes [10]. Prospective evaluation is consequently important: SafeToolBench tests whether a proposed action is safe before execution, using 1,200 adversarial instructions across 16 domains and four risk types. Its SafeInstructTool reached 83% average best performance for GPT-4o in the reported setting, but performance remained as low as 72.1% on a reported privacy/physical-injury setting [9].

Robustness also requires separating error types. Agent-SafetyBench used 349 interactive environments and 2,000 test cases across eight safety-risk categories and ten failure modes; none of 16 evaluated agents exceeded a safety score of 60%, and defense prompts alone were insufficient [9]. Recent auditing work reports 14,750 execution traces from 13 agents across four domains. Substring-heuristic judging agreed with human annotation only at chance level (Cohen’s kappa 0.049), while GPT-4o-mini reached 0.567 and dual annotators reached 0.835. Fabricated tool use appeared in 37.5% of Gemini-2.0-Flash traces in the study, and a runtime interceptor reduced hallucination by 23 percentage points for GPT-4o-mini and 24 points for Qwen2.5-7B [11]. These findings argue for trajectory inspection, calibrated judges, explicit tool-call logs, and runtime controls rather than a single success score.

## Trends and open problems
The last two years have moved the field toward long-horizon, multimodal, multi-application, and safety-aware evaluation [6][7][8]. The unresolved issue is not simply whether a larger model can call more tools, but whether it can preserve goals and constraints across many dependent actions. Current evidence leaves at least five open problems. First, planning and navigation remain bottlenecks even when local tool use is strong, as the gap between WebArena or OSWorld agents and humans demonstrates [6][7]. Second, memory needs standardized tests for long-range consistency and dynamic updates; the evaluation survey identifies both as persistent weaknesses [8]. Third, safety must be prospective and contextual: the same tool can be benign or dangerous depending on the instruction, permissions, and state [9][10]. Fourth, evaluators themselves are unreliable unless calibrated against human judgments [11]. Finally, agent quality should be reported as a vector—completion, cost, efficiency, reliability, recovery, and safety—rather than a single headline accuracy [11]. Progress will depend on reproducible environments, faithful execution traces, recovery tests, and interfaces that make authorization and uncertainty explicit.
